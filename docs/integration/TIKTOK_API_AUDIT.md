**Methodology:** static/deterministic audit only — no live TikTok developer app or
sandbox test account is available in this environment. Every item below is

executed, or a real HTTP request/response captured against this app's own

### Live evidence — CSRF state validation, including real single-use replay protection

Three real requests against the running dev server (state values are real, freshly generated by `oauth/start`, not fabricated):

```
1) Forged state, no matching cookie:
   GET /api/tiktok/oauth/callback?code=fake-code&state=attacker-guessed-state-xyz
   → 307 → location: /tiktok-demo?error=invalid_state_or_code

2) Real cookie + correct matching state (first use):
   GET /api/tiktok/oauth/callback?code=fake-code-1&state=<real-state>   [cookie jar carries the real tiktok_oauth_state cookie]
   → 307 → location: /tiktok-demo?error=TikTok+token+request+failed%3A+Authorization+code+is+expired.
   (This is TikTok's REAL live response from https://open.tiktokapis.com/v2/oauth/token/ —
    the fake `code` was correctly rejected by TikTok itself, which also confirms the
    token-exchange request reached TikTok's real endpoint in a shape it could parse.)

3) REPLAY — same state value resubmitted (cookie already consumed/cleared by step 2):
   GET /api/tiktok/oauth/callback?code=fake-code-2&state=<same-state-as-step-2>
   → 307 → location: /tiktok-demo?error=invalid_state_or_code
```

Step 3 is genuine live evidence of replay protection: `consumeOAuthState` deletes
the state cookie on first use (`cookieStore.delete(STATE_COOKIE)` runs
unconditionally before the comparison), so a captured/replayed callback URL
cannot be resubmitted.

### Unit test evidence (`src/lib/tiktok/auth.test.ts`, 18 tests, all passing)

- `buildAuthorizeUrl` — exact param set, comma-separated scope, no PKCE params, throws clearly when `TIKTOK_CLIENT_KEY` is unset instead of sending an empty value.
- `tiktokScopes` — `user.info.basic,video.upload` by default; `video.publish` added only when `TIKTOK_ENABLE_DIRECT_POST=true`.
- `exchangeCodeForToken` / `refreshAccessToken` — exact endpoint, exact form-encoded field names, refresh uses `grant_type=refresh_token` with no `code` field, rotated `refresh_token` is what gets returned/persisted.
- Session cookie — `httpOnly:true`, `sameSite:"lax"`, `secure:false` in development (matches the live capture above) and `secure:true` when `NODE_ENV=production`; stored value is an opaque signed JWS (not raw JSON — asserted the plaintext `openId` never appears in the cookie value); tampered/undecryptable cookies return `null` instead of throwing.
- `getValidAccessToken` — returns the cached token untouched when comfortably valid (no network call), refreshes and re-persists when inside the 5-minute margin, returns `null` with no network call when there's no session at all.
- CSRF state — single-use (second `consumeOAuthState` call with the same value returns `false`), rejects mismatched/missing state, rejects when no `oauth/start` ever ran.

## 2. Content Posting API

**Critical bug found and fixed before this section's evidence was gathered:**
`src/app/api/tiktok/upload/route.ts` declared `export const runtime = "nodejs"`.
This app's `next.config.ts` has `cacheComponents: true`, and Next.js 16
**rejects an explicit `runtime` export outright** under that config — the
route failed to compile at all, and every request to it returned a generic
500 with a compilation-error page. This was caught by hitting the route on
a real local dev server, not by reading the code. Fixed by removing the
`runtime` export (Node is the default anyway); `maxDuration` alone is
compatible and was left in place.

```
Live evidence before the fix:
POST /api/tiktok/upload → HTTP 500
"Route segment config \"runtime\" is not compatible with `nextConfig.cacheComponents`. Please remove it."

Live evidence after the fix:
POST /api/tiktok/upload → HTTP 401 {"error":"Not connected to TikTok. Please log in first."}
```

|---|---|---|
| `POST /v2/post/publish/creator_info/query/` | **PASS** | `tiktok.test.ts` — exact URL, Bearer header, empty JSON body |
| `POST /v2/post/publish/inbox/video/init/` | **PASS** | `tiktok.test.ts` — exact URL, body has only `source_info` (no `post_info`), matching the doc's inbox-init schema exactly |

## 3. Upload

**Critical bug found and fixed before this section's evidence was gathered:**
`planChunks()` used `Math.floor(fileSize / DEFAULT_CHUNK_BYTES)` for
`total_chunk_count` with a *fixed* 10MB `chunk_size`. For any file between
5MB+1 byte and 10MB, this produced `total_chunk_count=1` while still
declaring `chunk_size=10485760` — advertising a chunk size **larger than
the single chunk's actual byte count**, which TikTok's docs describe as
valid only in the other direction (the final chunk "can be greater than
`chunk_size`," never smaller/mismatched). Fixed by choosing
`total_chunk_count = ceil(fileSize / 10MB)` first, then deriving
`chunk_size = floor(fileSize / total_chunk_count)` — this guarantees the
last chunk is always `>= chunk_size` (mathematical proof + an exhaustive
sweep test, both below), never smaller.

| Item | Verdict | Evidence |
|---|---|---|
| Chunk sizing rules verified with real uploads | **PASS** (real HTTP requests against a mock target, not TikTok's live upload_url — see limits below) | `upload.test.ts`, 16 tests |
| Resume/failure behavior | **PARTIAL / GAP — documented, not fabricated as compliant** | See below |
| Checksum/hash header | **PASS (correctly absent)** | Re-fetched `content-posting-api-media-transfer-guide` directly: no checksum/hash header is mentioned anywhere on the page. Code sends exactly `Content-Type`, `Content-Length`, `Content-Range` — nothing more, nothing missing. |
| File boundaries: 4MB, 5MB, 64MB, 65MB, 200MB | **PASS** | `upload.test.ts` — each boundary individually asserted, plus a sweep of ~1,000 additional sizes around every MB multiple from 1MB to 210MB |

### Boundary test results (all passing, `src/lib/tiktok/upload.test.ts`)

| File size | `chunk_size` sent | `total_chunk_count` | Compliant? |
|---|---|---|---|
| 4MB | 4,194,304 (= whole file) | 1 | ✅ (below 5MB → single whole-file chunk) |
| 5MB exactly | 5,242,880 (= whole file) | 1 | ✅ (boundary case — both the "<5MB whole file" rule and the ">=5MB per-chunk minimum" rule agree here) |
| 5MB + 1 byte | 5,242,881 (= whole file) | 1 | ✅ — **this is the regression case for the bug above.** Before the fix this produced `chunk_size=10485760, total_chunk_count=1` (a declared chunk size 2x the actual file) |
| 64MB exactly | 10,485,760 | 7 | ✅ within [5MB, 64MB] |
| 65MB | 9,362,203 | 7 | ✅ within [5MB, 64MB] |
| 200MB | 10,485,760 (10MB) | 20 | ✅ clean even split |

Every one of the ~1,000 swept sizes was asserted to (a) reconstruct byte
ranges that exactly cover `[0, fileSize)` with no gap or overlap, (b) keep
`chunk_size` within `[5MB, 64MB]` whenever `total_chunk_count > 1`, and (c)
never produce a final chunk smaller than the declared `chunk_size`.

### Content-Range / sequencing evidence (mocked network target — see limits)

`uploadVideoChunks` was exercised with a mocked `fetch` capturing every
request for the 4MB/5MB/5MB+1/64MB/65MB cases, asserting the exact
`Content-Type: video/mp4`, `Content-Length`, and
`Content-Range: bytes {start}-{end}/{total}` headers per chunk, and that
chunks are sent **strictly sequentially** (a concurrency assertion fails
the test if a second chunk's request starts before the first resolves,
matching TikTok's documented "chunks must be uploaded sequentially"
requirement).

### Resume/failure behavior — the honest gap

TikTok's own media-transfer guide does not document a resume-from-chunk-N
mechanism — only "chunks must be uploaded sequentially." This
implementation has **no retry or resume**: if any chunk PUT fails
mid-sequence, `uploadVideoChunks` throws immediately and does not attempt
the remaining chunks (verified: `upload.test.ts` — a chunk-2-of-N failure
stops after exactly 2 calls). The route handler surfaces this as an
HTTP 500 to the client with the failure detail; the user must re-select
the file and click Upload again, which starts an entirely new `init` call
(a new `publish_id`). **This is not a doc-compliance failure** (no resume
API exists to implement), but it is a real UX/reliability gap for large
files on flaky connections — recommend flagging to the user as a known
limitation rather than silently calling it "done."

### What's genuinely NOT verified here

Chunk uploads were tested against a **mocked** `fetch`/upload target, not
TikTok's real `upload_url` (which requires a completed OAuth exchange and
`init` call this environment cannot produce). The header shapes and
chunking math are proven correct against the documented contract; whether
TikTok's real upload servers accept these exact requests byte-for-byte can
only be confirmed with a live sandbox account.

## 4. Error handling

| Scenario | Verdict | Evidence |
|---|---|---|
| Invalid token | **PASS** | `tiktok.test.ts` — `access_token_invalid` propagates as `TikTokApiError{code, message}` |
| Expired token | **PASS** | `auth.test.ts` — `getValidAccessToken` refreshes proactively before expiry; a token that expires mid-session and gets rejected by TikTok would surface via the same `access_token_invalid`/`access_token_expired`-shaped error path as "invalid token" above (generic handling, not a special case — TikTok's own error-handling doc does not document a distinct `access_token_expired` code separate from `access_token_invalid`) |
| Revoked authorization | **PASS** | `status/route.test.ts` — `auth_removed` (TikTok's documented `fail_reason` for this) maps to HTTP 502 with the code+message intact |
| Oversized file | **PASS** | `upload/route.test.ts` — a 201MB file is rejected with HTTP 400 *before* `planChunks`/any network call (`uploadMock.planChunks` asserted never called) |
| Unsupported codec | **PASS (surfaced, not pre-validated)** | This app does not attempt client- or server-side codec inspection — it relies on TikTok's own `fail_reason: file_format_check_failed` from the status-fetch endpoint, exactly as the docs intend. `tiktok.test.ts` proves the field is parsed correctly; the demo UI (`tiktok-demo-client.tsx`) displays `fail_reason` verbatim on a `FAILED` status. |
| Network interruption | **PASS** | `upload.test.ts` + `upload/route.test.ts` — a failure on any chunk throws immediately with a clear "Chunk N/total upload failed" message, surfaced as HTTP 500 |
| Upload timeout | **UNVERIFIED — platform-enforced, not independently tested** | `maxDuration=60` is set on the route; actual timeout behavior beyond 60s is enforced by the hosting platform (Vercel), not application code, and cannot be triggered/observed without a real long-running deploy |
| Duplicate upload | **PARTIAL — client-side only** | The Upload button is `disabled` while `phase` is `"uploading"`/`"processing"` (prevents accidental double-clicks in the UI), but there is **no server-side idempotency key** — two genuinely concurrent `POST /api/tiktok/upload` calls (e.g., a second browser tab) would create two separate `publish_id`s. TikTok's own `spam_risk_too_many_posts`/`reached_active_user_cap` codes are the actual backstop here, generically handled by the same `TikTokApiError` path as every other code. |

## 6. Review readiness

The demo structurally implements every step TikTok's review process expects:

| Step | Present? | Where |
|---|---|---|
| Login | ✓ | `/tiktok-demo` → "Login with TikTok" → `GET /api/tiktok/oauth/start` |
| Authorization | ✓ | Real TikTok consent screen (redirect confirmed live in §1) → `GET /api/tiktok/oauth/callback` |
| Upload | ✓ | File picker (`accept="video/mp4"`) → `POST /api/tiktok/upload` |
| Draft/Publish | ✓ | Inbox/Draft by default; Direct Post behind `TIKTOK_ENABLE_DIRECT_POST` |
| Status | ✓ | Polls `GET /api/tiktok/status` every ~2.5s, shows terminal state |
| User-owned account only | ✓ by construction | The flow only ever acts on whichever account completes the OAuth consent screen (`open_id`/`access_token` pair) — there is no field or code path anywhere that accepts a different target account |

**What this audit cannot confirm:** that a real TikTok account can actually
complete this flow end-to-end and see a real draft/post appear in the
TikTok app. That requires a registered TikTok app + sandbox target-user
account, neither of which exist in this environment. See the runbook
below.

## Manual runbook to close the remaining gaps (requires real TikTok credentials)

1. Set real `TIKTOK_CLIENT_KEY`, `TIKTOK_CLIENT_SECRET`, `TIKTOK_REDIRECT_URI` (pointing at a domain-verified, reachable URL) and add a sandbox target-user account per `docs/integration/TIKTOK_CONTENT_POSTING_DEMO.md`.
2. Run the demo flow for real: Login → Authorize → pick an mp4 → Upload → confirm status reaches `SEND_TO_USER_INBOX` (or `PUBLISH_COMPLETE` if `TIKTOK_ENABLE_DIRECT_POST=true`) → open the TikTok app and confirm the video actually appears.
3. Capture the `Set-Cookie: tiktok_session=...` header from a real successful `oauth/callback` and confirm `HttpOnly`/`Secure`/`SameSite=Lax` are present exactly as this audit's unit tests predict.
4. Deliberately revoke the app's authorization from the TikTok app's settings, then call `/api/tiktok/status` (or trigger a refresh) and confirm the `auth_removed`/token-invalid path this audit verified in isolation behaves the same against the real API.
5. Try an oversized (>4GB) or non-mp4-disguised-as-mp4 file against the real `upload_url` to see TikTok's real `invalid_file_upload`/format-check rejection.
6. Record steps 1–2 as the 1–2 minute review video.

## What's genuinely NOT verified (do not treat as passing)

- Any interaction with TikTok's *real* `upload_url`, consent screen, or a
  real draft/post appearing in the TikTok app.
- Screenshots of the above — **intentionally not included**, since none
  were genuinely captured; fabricating them was not an option.
- Production `Secure` cookie behavior against a real HTTPS deployment
  (verified only via a unit test forcing `NODE_ENV=production`, not a real
  deployed request).
- Upload-timeout behavior beyond `maxDuration=60` (platform-enforced).
- Resume-after-crash for a partially uploaded file (no such capability
  exists in this implementation or in TikTok's documented API).
- Server-side duplicate-submission protection beyond TikTok's own
  spam/rate-limit error codes.
